# Product media operations (Phase 5.3A)

This subsystem is exclusively for ordinary listing photos and profile photos. It must not be used for Veriff documents/selfies, biometric evidence, healthcare credentials, video, SVG, or other verification media.

## Supabase Storage

Create and configure these buckets in the Supabase Dashboard; the API does not create buckets:

| Bucket setting | Required policy |
| --- | --- |
| `SUPABASE_MEDIA_INGEST_BUCKET` (`media-ingest`) | Private. Accept only `image/jpeg`, `image/png`, and `image/webp`; set the bucket file-size limit to `MEDIA_MAX_INPUT_BYTES` (5 MiB by default). Do not add public read policies. Browser writes use short-lived signed upload URLs generated by the API. |
| `SUPABASE_LISTING_MEDIA_BUCKET` (`listing-photos`) | May be public. Contains only server-re-encoded WebP derivatives. Browser upload must not be permitted. |
| `SUPABASE_PROFILE_MEDIA_BUCKET` (`profile-photos`) | May be public. Contains only server-re-encoded WebP derivatives. Browser upload must not be permitted. |

The ingest bucket must differ from both derivative buckets in production. The service key is server/worker-only and must have object create/read/delete access to these three specifically configured buckets. Never expose it to a browser. Bucket-level limits are defense in depth; the API completion endpoint and worker enforce the same byte/MIME rules independently.

## API contract

- `POST /uploads/presigned-url`: authenticated. Body: `purpose`, `fileName`, `contentType`, and `listingId` for listing photos. Returns `uploadIntentId`, `uploadUrl`, expected private `storagePath`, `expiresAt`, and `maxBytes`. It never returns an original/public file URL.
- `POST /uploads/:intentId/complete`: same owner or Admin. Verifies the database-selected object, atomically moves the asset to `uploaded`, and creates the stable `media-process:<assetId>` outbox event. Repetition is idempotent.
- `GET /uploads/:intentId`: owner/Admin-safe state. Private ingest details are omitted. Ready variants are returned; provider errors are not.
- `DELETE /uploads/:assetId`: owner/Admin deletion by database asset ID.
- `PATCH /listings/:listingId/photos/:photoId/order`: listing owner/Admin reorder.
- `DELETE /listings/:listingId/photos/:photoId`: listing owner/Admin deletion. Legacy rows are retired in the database; processed objects use durable cleanup.
- `DELETE /users/me/profile-photo`: removes the active profile asset and schedules cleanup.

`POST /listings/:id/photos` no longer registers a client-provided storage path and returns `MEDIA_PROCESSING_REQUIRED`. `PATCH /users/me` rejects non-null `profilePhotoUrl`; use the media workflow. A null remains a compatibility clear operation, while the dedicated delete endpoint is preferred.

Published photo objects include `source: "processed" | "legacy"`. Current/public user DTOs retain `profilePhotoUrl` for compatibility and add `profilePhoto: { url, source } | null`.

## Processing policy

Inputs are limited by default to 5 MiB, 40 million decoded pixels, 12,000 pixels in either dimension, and one page/frame. The worker checks magic bytes and decoder format, computes SHA-256, applies EXIF orientation, and fully re-encodes to WebP quality 82 without metadata-preservation options. This strips EXIF, GPS, ICC, and comments.

- Listing: `listing_thumbnail` inside 480×480 and `listing_display` inside 1600×1600.
- Profile: centered square `profile_small` 96, `profile_medium` 256, and `profile_large` 512.
- No variant upscales a smaller source.
- Paths are deterministic: `media/<assetId>/<variant>.webp`.

Ready originals remain private for `MEDIA_INGEST_RETENTION_HOURS` (24 by default), then are removed. Rejected/deleted assets are eligible for immediate cleanup. Database state changes precede deletion, and cleanup reads only persisted paths.

## Deployment and recovery

Run the media worker independently from the email worker:

```text
npm run worker:media -w apps/api
npm run media:retry -w apps/api -- 25
npm run media:cleanup -w apps/api -- 100
```

Deploy `worker:media` as a continuously running process with graceful SIGINT/SIGTERM handling. Schedule `media:retry` and `media:cleanup` periodically (for example, every 5 minutes and hourly). The worker publishes only media outbox event types to the separate `media` BullMQ queue, uses the outbox row ID as the stable BullMQ job ID, limits concurrency with `MEDIA_PROCESSING_CONCURRENCY`, and recovers stale processing claims after 15 minutes.

## Legacy migration

Migration `20260723000000_add_secure_media_processing` preserves existing URLs and marks every existing `ListingPhoto` as `legacyUnprocessed=true`. Existing `User.profilePhotoUrl` values remain legacy when no active processed media asset is linked. They are explicitly labeled in DTOs and are not represented as sanitized. A future reprocessing/removal project may retire them; this phase does not download or process those historic objects.

## Environment

```text
MEDIA_PROCESSING_ENABLED=false
MEDIA_MAX_INPUT_BYTES=5242880
MEDIA_MAX_INPUT_PIXELS=40000000
MEDIA_MAX_DIMENSION=12000
MEDIA_PROCESSING_CONCURRENCY=2
MEDIA_INGEST_RETENTION_HOURS=24
SUPABASE_MEDIA_INGEST_BUCKET=media-ingest
SUPABASE_LISTING_MEDIA_BUCKET=listing-photos
SUPABASE_PROFILE_MEDIA_BUCKET=profile-photos
```

Enabling media processing in production additionally requires `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SECRET_KEY`, and `REDIS_URL`. Automated tests use the `MediaStorage` interface and do not contact Supabase.
